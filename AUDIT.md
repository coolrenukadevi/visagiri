## 1. Current architecture

There is no existing PHP application to modernize. What ships today at visagiri.com is a **static HTML export of a purchased ThemeForest template** ("RouteX – Immigration and Visa Consulting HTML5 Template," reskinned by an agency called RRDevs), plus two trivial procedural mail scripts. Concretely:

- **71 HTML files**, no templating/includes — every page repeats the full header/nav/footer markup inline. No component reuse mechanism exists.
- **2 PHP files total**: `mail.php` (root) and `new/sendemail.php` — both single-purpose contact-form mailers, no framework, no routing, no classes beyond one small `ContactForm` class in `mail.php`.
- **No database.** No `PDO`, no `.env`/config file, no schema anywhere in the export.
- **No authentication, sessions, dashboards, or admin panel** in any form.
- **CSS**: a vendor'd Bootstrap + custom SCSS/CSS build (`assets/css`, `assets/scss`) — a real, reasonably modern component library (cards, breadcrumbs, counters, etc.), but authored for a generic "immigration consulting" template, not a SaaS/fintech direction.
- **JS**: vendor bundle (Swiper, WOW.js, odometer, vanilla-tilt, etc.) — animation/carousel libraries typical of a marketing template, not app logic.
- **A second, incomplete redesign draft lives at `/new/`** in the same production webroot — a different, newer template (multiple unedited `index-2.html`…`index-4.html`, `coaching-details.html`…`-6.html` demo variants) with its own broken internal links, not linked from the live site nav, but publicly reachable today.
- **Two vendor documentation folders are also live in production**: `/jina/documention/` and `/new/Doc/` — the ThemeForest template's own doc pages, publicly crawlable.

**Conclusion:** nothing described in Phases 9–14 of the brief (auth, dashboard, admin, consultant panel, document management, application system) exists in any form. This is a from-scratch build on top of a brand asset (logo/colors) and a page-topic checklist, not a migration of working functionality.

## 7. Database requirements

Normalized MySQL 8 schema, PDO + prepared statements throughout, matching the table list from the brief:

`users`, `roles`, `countries`, `visa_types`, `country_visa_types` (join table — which visa types a country actually offers, since this varies), `visa_requirements` (the versionable content block: eligibility, documents, process, fees, processing time — each row carries `last_verified_at` + `source_url`, never silently overwritten), `embassies`, `consulates`, `vac_centers`, `applications`, `application_status_history`, `documents` (document type catalog), `application_documents` (uploaded files per application — private storage, randomized filename, MIME/size validated), `appointments`, `payments`, `notifications`, `messages`, `support_tickets`, `faqs`, `blog_posts`, `blog_categories`, `contact_enquiries`, `audit_logs`.

Roles table backs: Super Admin, Admin, Visa Consultant, Document Reviewer, Finance, Customer Support — each with a distinct permission set as specified in the brief (consultants see only assigned applications; finance sees payments only, etc.).

Every table gets `created_at`/`updated_at`; soft-delete (`deleted_at`) on `applications`, `users`, `documents` where audit history matters more than hard deletion. Foreign keys enforced at the DB level, not just app level.

This schema needs your §7-style sign-off on scope (e.g., exact document type list, exact status timeline stages) before table DDL is finalized — I'll draft it as part of Phase 1/2 of the sequence below and flag anything still open.

## 9. Customer dashboard plan

SaaS-pattern layout: fixed sidebar (Dashboard, My Applications, Documents, Appointments, Payments, Messages, Notifications, Profile, Support, Logout) + content area.

- **Dashboard home**: "Welcome back, [Name]" + 4 summary tiles (Active Applications, Pending Documents, Upcoming Appointments, Outstanding Payments) + application cards (Application ID, Country, Visa Type, Status, Progress %, Last Updated, Next Action).
- **Application detail**: visual status timeline (Created → Documents Submitted → Documents Verified → Payment Completed → Appointment Scheduled → Submitted → Under Processing → Decision Received → Completed), each stage stamped with date/time/consultant comment, sourced from `application_status_history`.
- **Documents**: per-document status (Required/Uploaded/Under Review/Approved/Rejected), upload widget with client + server-side validation, consultant re-upload requests with visible comments.
- **Payments**: outstanding/paid list, tied to `payments`.
- **Messages/Notifications**: threaded per-application messaging with consultants; system notifications for status changes.
- Session-gated throughout (`includes/auth.php`); every write action CSRF-protected; every document fetch goes through a private, authenticated download endpoint — never a direct public `/uploads/` URL.

## 10. Admin dashboard plan

Role-gated (`/admin/`, Super Admin / Admin / Consultant / Document Reviewer / Finance / Support), sidebar-driven, mirroring the customer dashboard's visual language so the whole platform feels like one system rather than two bolted-together products.

- **Admin dashboard home**: operational counts (Total/New Applications, Pending Documents, Under Review, Appointments, Payments, Completed, Open Support Requests).
- **Content management (this is the load-bearing feature of the whole platform)**: Countries, Visa Types, Visa Requirements, Embassies/Consulates/VACs — all editable through forms, never by touching PHP. Every requirements record has a mandatory "last verified" date + source field enforced at the DB/form level, so stale or unsourced info can't silently ship.
- **Operational management**: Applications (assign consultant, view/change status, timeline), Customers, Documents (approve/reject/request re-upload with comment), Payments (status, invoice generation), Appointments, Consultants (assignment/workload).
- **Content/marketing**: Blog posts + categories, FAQs, Testimonials (kept out of public view until a real, attributable, consented testimonial exists — no placeholder testimonials ship).
- **Enquiries**: contact form submissions land here (not just email) so nothing gets lost the way it has been.
- Role permission checks enforced server-side on every admin route, not just hidden in the UI; every state-changing action writes to `audit_logs`.

## Phase 16 (Security) — complete

A full audit sweep (SQL injection, XSS, CSRF coverage, IDOR/authorization, state-changing GETs, HTTP header injection, security-header completeness, auth timing side-channels, file/directory exposure, error handling, password policy, open redirects) across every layer built in Phases 2–15, run partly by hand and partly via an independent audit pass covering the newer admin/consultant panels specifically. The good news first: **no SQL injection, no XSS, no CSRF gaps, and no IDOR were found anywhere in the codebase** — the patterns established from Phase 2 onward (prepared statements everywhere, `e()` on every output, `csrf_field()`/`csrf_require()` on every mutating form, and per-resource ownership checks scoped to `user_id`/`assigned_consultant_id`) held up under a dedicated adversarial pass, including across the admin and consultant panels added in Phases 13–14.

Three real, fixable issues were found and fixed:

- **Login timing side-channel (username enumeration)** — `auth/login.php`'s `if (!$user || !verify_password(...))` let PHP's `||` short-circuit: a request for a non-existent email/mobile skipped the (deliberately slow) bcrypt comparison entirely, while a request for a real account with the wrong password paid that cost — both returned the identical generic error message, but the *response time* differed measurably, letting an attacker enumerate registered accounts by timing alone even though the message itself leaked nothing. Fixed by always calling `verify_password()`, against a precomputed dummy hash (`DUMMY_PASSWORD_HASH` in `includes/auth.php`) when no user is found, so both paths cost the same.
- **Logout was a GET-triggered state change** — every other mutation in the app is correctly POST + CSRF-gated, but `<a href="/logout/">` was a plain link, meaning any third-party page could force a visitor's session to end via something as simple as `<img src="https://visagiri.com/logout/">`. Low impact (forcing a logout isn't damaging), but inconsistent with the rule applied everywhere else. Converted every logout link (header, dashboard/admin/consultant sidebars) to a small POST form with a real CSRF token; `auth/logout.php` now rejects non-POST requests. Verified via screenshot that the button renders pixel-identical to the old link (no visual regression) and that clicking it actually ends the session (confirmed `/dashboard/` correctly bounces to `/login/` afterward).
- **Missing HSTS header** — `send_security_headers()` had no `Strict-Transport-Security`, leaving a theoretical SSL-stripping window on top of the HTTPS redirect `public/.htaccess` already forces. Added `max-age=31536000; includeSubDomains`.

One hardening improvement made even though the current runtime already prevents exploitation: the `Content-Disposition` filename in every document-download handler (dashboard/admin/consultant) was built from the uploaded file's original name with only quote-stripping — PHP's `header()` already refuses to emit any value containing a raw CR/LF, so this wasn't actually exploitable as HTTP response splitting today, but relying solely on one runtime's built-in protection isn't real defense in depth. Added `sanitize_uploaded_filename()` (strips control characters at upload time, before the name is ever stored) so the guarantee doesn't depend on PHP's internals alone.

**Reviewed and consciously left as-is, with reasoning recorded rather than silently ignored**:
- `style-src 'unsafe-inline'` stays in the CSP — the codebase uses inline `style="..."` attributes pervasively (37+ files), and stripping it would require a large, high-regression-risk refactor to move every inline style into classes or add nonces. Risk is low relative to `script-src` (already strict, no `unsafe-inline`/`unsafe-eval`) since no injectable vector into any `style="..."` attribute exists (confirmed during the XSS pass) — CSS-only injection has far less exploit potential than JS injection would.
- Password policy stays at an 8-character minimum with no complexity requirement — informational, not a defect; offset somewhat by rate-limited login/registration.
- Local `.env` currently has `APP_DEBUG=true`/`APP_ENV=local`, correct for this dev environment; `.env.example` already defaults to `false`/`production` so a real deploy starts from the safe default.

**Verified**: HSTS header present via curl; a GET to `/logout/` no longer destroys the session (confirmed via cookie-jar test); a real browser login → click the new logout button → confirmed the session actually ended (`/dashboard/` redirected to `/login/` afterward) with zero console errors and no visual difference from the old link-based button; all changed files pass `php -l`.

## Optional single-folder cPanel package — for hosts that can't repoint the document root

The standard deployment layout (this app's architecture since Phase 2) keeps `public/` as the only web-servable folder, with `includes/`, `database/`, `.env`, and `uploads/` as siblings one level up — genuinely unreachable by any URL, not just blocked by a rule. That requires the hosting account's document root to be pointed at `public/`. Many basic shared-hosting cPanel accounts can't do that; the document root is fixed at `public_html/`.

Rather than silently work around that, the tradeoff was put to the client directly: keep the stronger two-folder protection and accept a slightly fiddlier two-location upload, or flatten everything into one folder for a plain drag-and-drop `public_html/` upload, at the cost of `includes/`, `database/`, `.env`, and `uploads/` moving from "physically outside the web root" to "inside the web root, blocked only by `.htaccess`." The client chose to flatten.

**`bin/package-cpanel.sh`** (new) builds this alternate layout into a separate zip without changing how the app is developed day to day — it only reads the working tree and writes to a temp build directory, then patches the one line in `index.php` that actually differs between layouts (`$root = dirname(__DIR__)` → `$root = __DIR__`).

**Two real bugs found and fixed while building this**, not just theoretical: `index.php`'s five `require_once` lines were originally independent of `$root` (computed *after* them), so the flattened package 500'd on every route except static assets — fixed by computing `$root` first and routing every `require_once` through it, so the packaging script's single sed patch is enough to retarget the whole front controller. And `public/.htaccess`'s static-file bypass previously allowed any existing file *or directory* through without going via `index.php`; harmless in the two-folder layout where nothing but `public/`'s own contents live there, but in the flattened layout that would let a request resolve straight to a real PHP file/directory (`attestation/index.php`, `dashboard/`, etc.) and get executed by Apache directly, skipping session setup, security headers, and routing entirely. Fixed by excluding `.php` files and directories from the bypass, and adding an explicit `[F,L]` deny rule for `includes/` and `database/`.

**Verified**: ran the packaging script end-to-end, extracted the resulting zip standalone (no `public/` folder, everything flattened), pointed a fresh PHP dev server at it against the real local database, and confirmed `/`, `/attestation/`, `/countries/`, `/visa/usa/`, `/leadership/`, `/our-team/`, and a static asset all return 200 with zero errors in the server log; confirmed `asset_url()`-generated cache-busting versions match real file mtimes in the flattened layout, not a `time()` fallback; `php -l` clean across every file in the package. **Not verified**: the `.htaccess` deny/bypass rules themselves, since this sandbox has no Apache installed to test against — the client should confirm after deploying that `https://yourdomain.com/includes/config.php` and `https://yourdomain.com/database/schema.sql` do not return raw file contents.

**Architecture decision**: unlike HRMS (which the client's own spec required at a separate `/hrms/` URL with its own login), this spec frames Forex as "CRM menu: Forex → ..." within the existing CRM, and section 2's "Search Existing Customer... in CRM" plus section 35's Step-1-through-Step-9 wizard (Customer → Travel → Visa → Forex Requirement → Documents → Quotation → Compliance → Payment → Delivery) describes a staff-driven workflow, not a public self-service form — a real customer would never fill in their own "Approval" or "Delivery" step. So Forex lives at `/admin/forex-*` (new admin sub-pages, same session/login/RBAC as the rest of the CRM, added as a new "Forex" section in the existing sidebar), with the one genuinely public piece being `/forex/track/` (reference number + registered mobile, non-enumerating, mirroring this project's other public lookup pages — `/track-visa/` itself no longer exists in this codebase, having been removed during an earlier no-database phase and never restored, so this was built fresh from the same established pattern rather than literally copied).

**Database**: `database/schema-forex.sql` adds 10 tables — `forex_rates` (admin-maintained buy/sell rates, never auto-fetched from a live API in this phase), `forex_country_rules` (admin-editable, drives the automatic document checklist per section 18 — ships completely empty, since this project never asserts a country's visa requirement as fact without an authorized user entering it; a country with no rule yet falls back to the full standard checklist, never to "nothing required"), `forex_requests`, `forex_documents` (verification fields live directly on the document row rather than a separate `forex_document_verifications` table — simpler, still fully satisfies "every document must have a verification status" since it's a strict 1:1 relationship), `forex_declarations`, `forex_quotations` (every quotation is a permanent, immutable snapshot — a rate change in `forex_rates` never touches an existing row here), `forex_approvals`, `forex_payments`, `forex_deliveries` (total amount only in Phase A — denomination breakdown is Phase B), `forex_status_history`. `customers` gained `pan_number_encrypted`/`pan_number_hash` via `ALTER TABLE`, reusing the exact same AES-256-GCM + searchable-hash pattern already used for passport numbers (`includes/encryption.php`) — PAN is exactly as sensitive and gets exactly the same treatment, not a new one. `database/seed-forex.sql` adds four new roles (Forex Manager, Forex Executive, Compliance/Audit, Accounts) and 15 `forex.*` permissions; the spec's fifth role, "Sales/Travel Consultant," was **not** built as a new role — the existing `visa-consultant` role already matches that exact description (scoped to assigned records, create-only, no approval rights), so it was simply granted the relevant `forex.*` permissions instead of creating a near-duplicate role. `current_admin_forex_scoped_to_assigned()` (`includes/rbac.php`) mirrors the already-proven `current_admin_hrms_scoped_to_assigned()` pattern rather than inventing a new one.

**The compliance-gated delivery control (section 17, the spec's own "extremely important" requirement)**: `forex_delivery_blockers()` (`includes/forex.php`) is the single source of truth for whether a request can be delivered — it re-fetches everything itself from the database rather than trusting caller-supplied state, so the document-completion checklist a staff member sees can never disagree with what the hard gate actually enforces. It checks, in order: customer identity (passport + PAN numbers) on file; passport and PAN documents verified; air ticket and hotel verified where the country rule (or the safe default) requires them; **visa copy verified when visa status is "Visa Available" or "eVisa," or a hand-signed, verified Visa-on-Arrival/Visa-Free declaration when visa status is "Visa on Arrival" or "Visa-Free"** — the spec's core visa-vs-declaration branch; an outright block when visa status is "Not Available," "In Process," or "Other," using the spec's exact warning text; payment confirmed as `paid`; and a completed approval. `admin/pages/forex-requests.php`'s `mark_delivered` action enforces this same function server-side before allowing delivery — a user without `forex.delivery.manage` gets a real `403`, not a hidden button (verified directly, see below). An authorized override (a distinct `forex.delivery.override` permission) is possible, but requires a written reason and writes a permanent `forex_approvals` row capturing the exact list of blockers overridden, the reason, the approver, and the IP address — never a silent bypass.

**File naming and document history**: uploads are renamed to `{reference}-{DOCTYPE}-{random}.ext` (e.g. `VG-FX-2026-000001-PASSPORT-39789bef01966b3c.pdf`) per section 28, never the customer's original filename. Replacing a document (e.g. after a rejection) creates a new row and marks the old one `is_current = 0` with a `deleted_at` timestamp — full history preserved, exactly per section 9's requirement, verified directly (see below).

**A real, pre-existing bug found and fixed during this pass's verification — not introduced by this module, but exposed by it**: `admin/pages/forex-requests.php`'s search query reused the same named PDO placeholder (`:search`) six times in one `OR`-chained `WHERE` clause. This project's database connection explicitly sets `PDO::ATTR_EMULATE_PREPARES => false` (real, non-emulated prepared statements) precisely because emulated prepares can mask SQL-handling bugs — but real prepared statements do not support the same named placeholder appearing more than once in a single query, and hit it with a fatal `PDOException: Invalid parameter number` the moment a real search term was typed. A project-wide grep for the same anti-pattern found it already present, unnoticed, in **three previously-shipped files**: `admin/pages/customers.php` (Phase 1 CRM), `hrms/pages/candidates.php` (HRMS Phase A), and this session's own `admin/pages/forex-fema-audit.php` — every one of them would have thrown the identical fatal error the first time a real user typed a non-empty search term, and none of it was caught by any previous verification pass because none of them had actually exercised those search boxes with a real term end-to-end. Fixed in all four files by giving each placeholder occurrence its own name (`:search1`, `:search2`, …) bound to the same value, then re-verified the customer search, HRMS candidate search, and forex reference-number search all now return real results with zero errors.

**Verified end-to-end against the real local database**, via `curl` with real cookie-jar sessions, real CSRF tokens, and real multipart uploads, working through every one of the spec's own 10 named test scenarios: **Test 1** (full happy path) — created a real Forex Manager account, added a real USD rate, created a request with `visa_available` status, uploaded and verified all five required documents (passport/PAN/air ticket/hotel/visa), created a quotation (2,000 USD × ₹83.25 = ₹166,500 base + ₹826 charges = ₹167,326 total, calculated correctly), approved it, recorded payment as `paid`, and successfully marked it delivered once every blocker cleared. **Test 2** — a request with `visa_available` but no visa document uploaded correctly blocked delivery with "Visa copy not uploaded." **Test 3** — a `visa_on_arrival` request correctly required a signed declaration instead of a visa copy in both the checklist and the delivery gate; uploading and verifying the declaration cleared that specific blocker. **Test 4** — an unverified PAN document correctly kept the request blocked ("PAN copy is uploaded but not yet verified"). **Test 5** — rejecting the passport document correctly blocked delivery with the rejection reason surfaced. **Test 6** — after creating the quotation, the master USD rate was changed from 83.25 to 90.00 in the rate table; the existing quotation's rate and total amount were confirmed completely unchanged, proving the immutable-snapshot design works under a real rate change, not just in theory. **Test 7** — a real Forex Executive test account (lacking `forex.delivery.manage`) attempted delivery directly via a forged POST and was correctly rejected with a genuine `403`, with the request status unchanged. **Test 8** — the Forex Manager overrode a blocked delivery with a written reason; confirmed a permanent `forex_approvals` row was created capturing the exact blocker list, the reason, the approver's ID, and the IP address. **Test 9** — replacing a rejected passport document was confirmed to leave the old row intact (`is_current = 0`, `deleted_at` set) while the new upload became current and `pending` again. **Test 10** — searching by `VG-FX-2026-000001` returned the request, and its FEMA/audit record view showed the complete status history from creation through delivery. Additionally confirmed: the public `/forex/track/` page shows the correct customer-safe timeline for a matching reference+mobile pair and the same generic "couldn't find a matching" message for a mismatched mobile (non-enumerating, per this project's established pattern); a delivered transaction correctly could not be deleted (no delete button rendered, and a forged delete POST was also rejected server-side). **Every test artifact — all test requests, customers, documents, quotations, approvals, payments, deliveries, declarations, rates, audit-log rows, and both test Forex accounts — was removed from the database and `storage/forex-documents/` before finalizing.**

**Not yet built, deferred to Phase B per the agreed plan**: payment gateway integration (Phase A is manual status entry only); denomination-level delivery breakdown (`forex_denominations` — Phase A records only the total amount delivered); customer-facing PDF quotation generation and the Download PDF/WhatsApp/Email send buttons; declaration template management with `{{variable}}` substitution and version history (Phase A supports uploading and verifying a signed declaration with its required metadata, but not a generated, admin-editable template); a friendlier country-rules admin workflow (the current one is a functional but plain CRUD form); automated candidate/HR email notifications (same honest constraint as HRMS — no SMTP configured yet); full reports (currency-wise, country-wise, pending-compliance, delivery, payment, audit/FEMA) and CSV/Excel/PDF export — the FEMA/audit view built in Phase A is read-only; and the customer portal tie-in. This is also explicitly a record-management tool, not a claim of FEMA/RBI legal compliance — every compliance-facing screen says so directly, and the country-rules table ships empty specifically so no legal assumption is baked in without the company's own authorized compliance/legal review.

## Primary header nav — icons added to every top-level tab

Client request: add icons to the main site header's top-level nav tabs (Visa Services, Attestation, Countries, Visa Process, Visa Updates, Company). A new `primary_nav_icon()` helper (`includes/functions.php`) was added rather than reusing `company_nav_icon()` directly, but deliberately matches its exact visual language — 16px, `viewBox 0 0 20 20`, `stroke="currentColor"`, `stroke-width="1.6"`, rounded caps/joins — so a top-level tab icon and the icons inside its own mega-menu (e.g. Company's trigger icon next to the "About Us"/"Leadership"/"Partners" icons in its mega-menu) read as one consistent icon system rather than two unrelated sets. Six icons were designed: a passport-style card for Visa Services, a certificate-with-checkmark for Attestation, a globe (circle + meridian ellipse + equator line) for Countries, two connected nodes for Visa Process (reflecting the step-by-step nature of that page), a bell for Visa Updates, and a two-building skyline (reusing the existing "building" visual idea already established in the Company mega-menu) for Company.

`includes/header.php` was updated on both the desktop nav and the mobile accordion menu — six insertion points each — wrapping each icon+label in a `.site-header__nav-icon` span. One layout bug was caught before shipping: the three mobile `<summary>` accordion triggers (Attestation, Countries, Company) rely on `display:flex; justify-content:space-between` to keep their label on the left and the "+"/"×" expand indicator on the right; dropping a bare icon span directly inside `<summary>` would have made it a third flex child and broken that spacing. Fixed by wrapping icon+label together in a single `.site-header__mobile-summary-label` span so the layout still sees exactly one content item plus the indicator.

`public/assets/css/layout.css`: top-level nav links became `inline-flex` (desktop) / `flex` (mobile) containers with a small gap; `.site-header__nav-icon` defaults to a muted color and transitions to the brand blue in sync with its parent link's own hover/active color rule, so icon and label always change color together rather than looking like two separate elements. Changing `.site-header__mobile a` from `display:block` to `display:flex` was checked against the existing CSS first — the more specific `.site-header__mobile-accordion-body li a` rule already overrides `display:block` for links nested inside an opened accordion, so this change only affects the six true top-level mobile items as intended.

**Verified visually** with Playwright at both 1440×900 and 390×844: all six desktop icons render aligned with their labels with no overflow; hovering the Company tab correctly turns both its icon and label blue while opening its mega-menu; the mobile hamburger menu shows all six icons correctly aligned, and opening the Attestation accordion confirms the icon/label/indicator layout holds with the panel expanded (the accordion body's own pre-existing category icons continue to render underneath, unaffected). No functional code was touched — this is markup/CSS/icon-helper only.
